# Cove Resonance V2

> Accepted on 2026-09-28.

这份文档记录 **Cove Resonance V2 相对最初公开 tag `v1-public-preview` 的变化**，以及 V2 当前完整能力、真实验收范围、已知边界和下一阶段建议。

## 版本基线

V1 基线：

```text
tag: v1-public-preview
commit: 021b241
```

V1 当时已经具备：

- 网易云一起听邀请识别与自动接受；
- 一起听房间进入 / 基础退出；
- ChatRoom 双向聊天；
- 当前歌曲 / 播放进度读取；
- 换歌、暂停、继续播放事件响应；
- 整首歌词与当前位置歌词；
- 网易云账号搜索、歌单、喜欢、历史、每日推荐；
- Conversation / State 基础事件语义；
- poll / SSE / EventSource Listener。

所以这些能力属于 V1 基线，不作为 V2 新增重复计算。

## V2 更新了什么

### 1. NIM realtime 成为播放状态主数据源

V1 已经能够解码 NIM realtime 播放事件，但播放状态主链路还没有完全切过去。

V2 完成了这一步：

- PLAY / PAUSE / GOTO / PROGRESS 直接驱动当前播放状态；
- HTTP 不再承担高频主状态来源；
- HTTP 主要用于房间生命周期、低频 reconcile 和 realtime 断线 fallback；
- stale `serverSeq` 会被丢弃；
- realtime timing anchor 用于推进当前播放进度；
- 暂停时进度停止，恢复时重新增长；
- 换歌时刷新 anchor。

这让播放状态从“能读到 realtime”升级成了“以 realtime 为准”。

### 2. ChatGPT 可以真正控制一起听播放

V2 新增：

```text
PAUSE
RESUME / PLAY
GOTO
NEXT
```

控制成功不以一次 HTTP 返回为准，而是等待匹配的 **NIM realtime confirmation**。

也就是说：

```text
ChatGPT 发控制
→ NetEase 上报
→ NIM realtime 回来
→ Bridge 确认状态真的变了
→ tool 才返回成功
```

### 3. 新增队列控制 ENQUEUE_NEXT

V2 新增：

```text
ENQUEUE_NEXT
```

修改 Together playlist 后不会直接宣告成功，而会重新读取 playlist，确认：

- `displayList`；
- 目标歌曲与当前歌曲的相邻位置；
- playlist version。

### 4. GOTO 假成功保护

真实测试中发现：

> 当目标 songId 不在当前 `displayList` 时，网易云可能广播“对方刚刚切歌了”，但手机端并不会真正切过去。

因此 V2 增加 guard：

- GOTO 前先读取 Together playlist；
- 目标不在 `displayList` 就直接拒绝；
- 要求先 enqueue，再执行 GOTO。

这样不会把协议广播误判成真实播放成功。

### 5. MCP profile 隔离

V2 新增公开 Music profile：

```text
/mcp/music
```

同时继续保留：

```text
/mcp
```

作为兼容入口。

`/mcp/music` 只消费 `netease.*` 事件，同时保留 Bridge 通用工具，避免不同外部域互相污染。

公开版 V2 的范围是：

```text
Bridge
+ NetEase
+ default/music profiles
```

Home / Reading / Spicy 等内部垂直模块不属于这个公开仓。

### 6. Bridge / Widget 路由加固

V2 对 Listener 和消息终态做了进一步整理：

- Widget 继续使用稳定 resource URI；
- Host 人工确认场景下，取消后的事件进入 terminal dismissed；
- 已终止事件不会被重复复活；
- Queue ordering、ACK、reply route、reply dedupe 和 source filter 继续保持统一语义；
- Bridge app / tools / event routing 被拆分成更清楚的模块。

### 7. Long-wait MCP Listener

V2 新增：

```text
cove_bridge_wait
cove_bridge_wait_ack
```

它用于 Host 对主动 `ui/message` 有人工确认或前台限制时的另一条正式投递路径。

流程：

```text
用户明确要求开始监听
→ cove_bridge_wait
→ 外部事件进入 Queue
→ wait 返回
→ cove_bridge_wait_ack
→ 处理事件
→ required routed reply（如有）
→ next wait
```

单次等待上限目前为 45 秒。

timeout 是正常边界。用户仍明确要求继续监听时，可以继续下一轮 wait。

模型侧 Long-wait ACK 与 Widget Listener 的 app-only delivered 路径已经分开。

### 8. required reply 完整闭环

对于网易云 ChatRoom 这类必须沿原路回复的事件：

```text
reserve
→ wait 返回
→ ACK
→ cove_bridge_reply
→ next wait
```

如果上一条 required event 还没有完成 routed reply：

```text
awaitingReply=true
```

下一次 wait 不会绕过 backpressure 去取下一条 conversation event。

已经 ACK / 回复过的旧事件不会在重新启动 Listener 后再次作为新消息释放。

## V2 正式部署时怎么选 Listener

V2 保留两条正式监听路线，共用同一个 Bridge Queue，但 **一次只能选择一条**。

| 路线 | 工作方式 | 截至 2026-09-28 的实测 |
| --- | --- | --- |
| Widget Listener | 外部事件到达后，经 Widget + `ui/message` 主动投进 ChatGPT | 网页端会出现人工确认；桌面端当前不可用；手机端（iOS）可用 |
| Long-wait MCP | 用户先开始一个模型 turn，由 `cove_bridge_wait` 等待未来事件 | 网页端、桌面端、手机端均已跑通 |

推荐：

- 需要多端兼容：优先 **Long-wait MCP**；
- 主要在手机端使用，并希望保留“外部事件主动敲门”的交互：可以选 **Widget Listener**；
- 不要同时启动两者，否则会竞争同一个 Queue。

Long-wait 不等于后台常驻。它需要一个已经开始的模型 turn，也仍受 Host 更高层的总时长 / tool-call 生命周期约束。

### 9. authoritative Together leave

V2 新增：

```text
netease_together_leave
```

退出请求之后会重新读取 authoritative room status。

只有确认账号已经真正离开房间，tool 才返回成功。

如果本来就不在 Together 中：

- 返回 confirmed no-op；
- 清理本地 room / realtime 状态；
- worker 回到等待下一次邀请。

## 已知边界

### Queue 仍是内存态

Bridge 重启后，尚未完成的 pending / reserved event 目前不能 durable recovery。

### Long-wait 不是永久后台任务

它依赖一个已经存在的模型 turn。

V2 真实验证了多轮 timeout 和数分钟等待，但没有声称所有 Host 都能无限期维持同一个 turn。

### SSE / reconnect 仍值得长期压力测试

极端网络抖动、长时间断线、多 Listener 竞争仍有继续加固空间。

### Together 控制成功不等于媒体版权可播放

房间控制、NIM realtime confirmation 和客户端媒体版权属于不同层。

V2 不用 IP spoof 或不必要的媒体 preflight 掩盖这一边界。

## 下一阶段建议优化

以下是 Roadmap，不是当前已实现能力。

### P0 — SQLite 持久化 Queue

建议优先持久化：

- event payload；
- event lifecycle；
- pending / reserved / delivered；
- reservation owner / timestamp；
- required reply state；
- routed reply dedupe key；
- state stream 最新值；
- retry / release 信息。

目标：Bridge 重启后可以恢复尚未完成的消息和回复。

### P0 — restart recovery / reservation lease

在 SQLite 基础上继续补：

- reservation TTL；
- worker 崩溃自动 release；
- required reply 恢复；
- delivered / replied terminal state；
- state event compaction；
- conversation event 不丢失、不重复回复。

### P1 — Listener watchdog

- heartbeat；
- reconnect backoff；
- listener health；
- last-success / last-error；
- reconnect count；
- 自动恢复。

### P1 — multi-listener ownership

后续可以考虑：

- listener lease；
- consumer identity；
- single-active-listener lock；
- explicit handoff；
- profile-scoped ownership。

### P1 — observability

建议增加：

- structured logs；
- event latency；
- reserve → ACK latency；
- ACK → reply latency；
- realtime reconnect count；
- queue depth；
- routed reply failure；
- control confirmation latency。

### P2 — 部署体验

- systemd 模板；
- Docker / Compose；
- 启动前配置校验；
- health / readiness endpoint；
- 升级 / 回滚说明。

### P2 — secrets

- Cookie / token 不落日志；
- NIM credentials 只留后端；
- secrets rotation；
- 环境变量校验；
- 可选外部 secret store。

## Release discipline

- 不为了测试长期保留临时 worker；
- 不因为媒体地区问题随便加 IP spoof；
- 不把未决定采用的实验功能直接并入正式路径；
- 不对已经工作的 NIM 连接再启动第二套登录；
- 不用 `git reset --hard` / `git clean` 解决来源不明的 working tree 问题；
- release 前跑 test、build、diff / secret check；
- 不为了“架构更优雅”重写已经被真实端到端证明过的底层。
